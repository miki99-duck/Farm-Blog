# 第 5 章 · 记忆与会话管理

> 本章目标:实现"多轮对话"。核心认知在第 1 章已验证——模型没有记忆,
> 所以**记忆是你自己维护的消息列表**。本章解决它的两大难题:历史太长怎么办?
>
> 对应 demo:`manual_history.py`、`trim_messages.py`、`summary_memory.py`

---

## 1. 版本须知:1.0 时代没有 Memory 类

0.x 旧教程会教你 `ConversationBufferMemory`、`ConversationSummaryMemory`——**1.0 已全部移除**。
官方思路是:记忆不是框架魔法,就是**你维护的 messages 列表**;裁剪与压缩是两个工具函数。
本尊手写一遍,比调用黑盒类学得透,且代码量并不多(每个 demo 不到 60 行)。

## 2. Demo 5-1 · manual_history.py:最简记忆

```
        ┌─────────────── 你的程序(记忆的真正主人)───────────────┐
        │                                                        │
        │  history = [system, human1, ai1, human2, ai2, ...]     │
        │      │  ▲                                              │
        │      ▼  │ append 回复                                  │
轮次:  用户说 ─┴─> llm.invoke(history) ──> AIMessage             │
        └────────────────────────────────────────────────────────┘
```

三个关键动作,缺一不可:

1. 用户输入 `append` 进列表;
2. **整个列表**发给模型(不是只发新输入);
3. 模型回复**也** `append` 回列表——否则下一轮模型看不到自己说过什么,会出现自我矛盾。

demo 第三轮问"回到第一个问题",模型能答,因为前两轮的完整历史都在。

**多会话怎么办?** 用 `dict[session_id, list]`。Web 应用里这个列表应该存进 Redis/数据库(Redis 是一款常用的"高速便签柜"式数据库),
而不是进程内存(重启即失忆)——记忆的持久化永远是**你的存储选型问题**,框架不替你选。

## 3. Demo 5-2 · trim_messages.py:上下文裁剪

历史每轮都在涨,两条红线:
**成本**(token 按量计费)与**窗口上限**(超限直接报错)。
`trim_messages` 按"预算"保留最近的完整轮次:

```python
from langchain_core.messages import trim_messages

trimmed = trim_messages(
    history,
    max_tokens=600,           # 预算(配合下面的计数函数)
    token_counter=count_chars,# 自己提供计数方式
    strategy="last",          # 保留最近的
    include_system=True,      # system 永远保留
    start_on="human",         # 裁后开头必须是 human
    end_on="ai",
)
```

为什么需要 `start_on="human"`:按预算"硬切"可能切在对话中间,导致列表以 AIMessage 开头——
模型看到"自己凭空说了半句话"会输出混乱。`trim_messages` 会**整轮整轮**地取舍,保证对话成对完整。

demo 用字符数做近似 token 计数(中文 1 字 ≈ 1 token 上下,足够教学);
生产中想精确,换成 `token_counter=llm`(用模型自己的 tokenizer)。
注意**语义陷阱**:裁剪是"扔掉旧信息"。如果用户第 1 轮说的关键偏好被裁掉,后面就会"失忆"——
这正是下一个 demo 要解决的。

**预期输出(demo 内含断言校验)**:

```
裁剪前:25 条消息,约 711 字符
裁剪后:21 条消息,约 595 字符
  [ system] 你是一位简洁的旅行规划师。...
  [   human] 帮我规划成都的三日行程...
  ...
裁剪通过:system 保留、从 human 开始、对话轮次完整。
```

## 4. Demo 5-3 · summary_memory.py:摘要压缩

裁剪丢信息,摘要是折中:**把旧对话用一次便宜的 LLM 调用压缩成要点**,最近的几轮保留原文:

```
[system, [旧对话压缩成的摘要], 最近 2 轮原始消息, 新输入]
```

demo 的实现套路(你可以直接抄):

```python
def summarize(old_messages, llm) -> str:
    prompt = [
        SystemMessage(content="把以下对话压缩成不超过 100 字的要点摘要,保留用户的关键偏好与决定。"),
        HumanMessage(content="\n".join(f"{m.type}: {m.content}" for m in old_messages)),
    ]
    return llm.invoke(prompt).content
```

demo 模拟了 4 轮咖啡店点单(冰美式少冰、加燕麦奶、牛奶过敏……),第 4 轮后触发压缩,
再用压缩后的历史问"明天照上次那样再来一杯"——模型从摘要里找回了偏好。
**摘要提示词里"保留用户的关键偏好与决定"这半句是灵魂**:它告诉压缩模型该保什么。

### 三种策略怎么选

| 策略 | 成本 | 保真度 | 适用 |
|------|------|--------|------|
| 全量历史 | 最高 | 100% | 短对话、demo、预算充足的内部工具 |
| 裁剪 trim | 低 | 丢弃旧的 | 大多数客服/问答场景(旧话不重要) |
| 摘要 + 近几轮原文 | 中 | 要点保留 | 长会话、偏好类助手(旧话重要) |

## 5. 常见坑

1. **忘记 append AI 回复** —— 模型下一轮看不到自己说过什么,反复道歉或自相矛盾;
2. **历史无限增长** —— 没有任何裁剪,长会话必然撞窗口上限(报 context length 错误);
3. **摘要每轮都做** —— 摘要本身也是一次 LLM 调用,应设阈值(如每 5 轮或超 N token 才压一次);
4. **system 消息被裁掉** —— 忘了 `include_system=True`,人设丢失,语气全变;
5. **多会话串号** —— Web 高并发下用全局单列表,用户 A 看到用户 B 的历史;会话隔离从第一天就要做对。

## 6. 小结与练习

记忆 = 你维护的消息列表;历史太长 = trim_messages 裁剪或摘要压缩。
