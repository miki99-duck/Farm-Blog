# 第 3 章 · 结构化输出:让模型返回"程序能用的数据"

> 本章目标:告别解析模型输出中的 JSON 字符串。学会用 `with_structured_output` +
> Pydantic 拿到**强类型对象**,并用"分类→路由"组合拳解决真实业务问题。
>
> 对应 demo:`extract_structured.py`、`nested_schema.py`、`classifier.py`

---

## 1. 问题:自然语言不是程序的"接口格式"

模型默认返回自由文本。程序要消费这份输出,老办法是提示词里写"请以 JSON 格式返回…",然后:

```python
import json, re
raw = response.content
data = json.loads(re.search(r"\{.*\}", raw, re.S).group())  # 一旦模型多说一个字就崩
```

脆弱的三连坑:模型包了 markdown 代码围栏、字段名随手改名、该返回数组时返回了字符串。
`with_structured_output` 把这一切变成一行:

```python
extractor = llm.with_structured_output(PersonInfo)
info: PersonInfo = extractor.invoke("...")   # 直接是 Pydantic 对象
```

先解释两个新名词,本章到处都是:

- **Pydantic**:Python 生态最流行的"数据说明书"库,用它描述"我想要的数据长什么样";
- **schema(模式)**:就是那份"数据说明书"本身——有哪些字段、什么类型、什么含义。

**原理一句话**:LangChain 把你的"数据说明书"转成模型厂商的"结构化输出"约定发给模型,
模型按约定生成,LangChain 再把返回数据组装成对象并**自动检查**——字段类型不符会直接报错,
错误在程序入口就暴露,而不是污染下游逻辑。

## 2. Demo 3-1 · extract_structured.py:基础抽取

schema 定义(给模型看的"表格"):

```python
class PersonInfo(BaseModel):
    """从文本中抽取的人物信息。"""          # <- 模型也会读这个 docstring

    name: str = Field(description="人物姓名")
    age: int | None = Field(default=None, description="年龄,文中未提及则为 null")
    city: str = Field(description="居住城市")
    hobbies: list[str] = Field(description="爱好列表")
```

写 schema 的三个要点:

1. **`Field(description=...)` 不是注释,是提示词的一部分**——写得越清楚,抽取越准;
2. **可选字段用 `int | None` + `default=None`**——告诉模型"没提到就说没有",避免它硬编一个值;
3. **类型尽量具体**——`age: int` 而不是 `age: str`,模型会约束输出为数字。

**预期输出**:

```
姓名:王小雨
年龄:28
城市:成都
爱好:['爬山', '做手冲咖啡', '学尤克里里']
类型确认:info 是 PersonInfo,可直接 info.name 访问
```

## 3. Demo 3-2 · nested_schema.py:嵌套与批量

真实业务的数据结构是嵌套的,Pydantic 直接支持:列表字段里装子模型(`list[Company]`)。

demo 同时演示 **batch**——一次并发抽取三条新闻:

```python
results: list[NewsAnalysis] = analyzer.batch([f"分析这条新闻:{s}" for s in SAMPLES])
```

`batch` 底层并发调用,返回顺序与输入一致。它不只省事:对**多条独立输入**(多篇文章、多个用户问题),
一条条 invoke 是串行等待,batch 能把总耗时压到接近最慢一条。

注意 `sentiment` 字段的写法约束了取值范围,demo 3-3 把这个技巧推到极致。

## 4. Demo 3-3 · classifier.py:枚举分类 + 条件路由

### 4.1 用 Literal 锁死类别

```python
from typing import Literal

class Intent(BaseModel):
    category: Literal["退换货", "产品咨询", "投诉"] = Field(description="用户意图类别")
```

`Literal` 是 Python 的类型标注写法,意思是"这个字段的值只能是列出的这几个"——它让模型只能三选一。如果用普通 `str`,模型可能返回"退货退款相关"、"consumer complaint"等
自由发挥的值,路由字典直接 KeyError。

### 4.2 分类 → 路由 → 生成

客服机器人不能"一套提示词打天下":投诉要安抚、咨询要专业、退换货要给流程。经典三段式:

```
用户输入 ──> [分类链] ──> Intent 对象 ──> 按类别选 system 提示词 ──> [回答链] ──> 回复
```

```python
intent: Intent = classifier.invoke({"question": q})     # 第一段:分类
system_prompt = ROUTES[intent.category]                  # 第二段:路由(字典查表)
reply = answerer.invoke({"system_prompt": system_prompt, "question": q})  # 第三段:生成
```

这个"结构化输出当路由器"的模式,是客服分流、工单系统、多技能助手的通用骨架——
也是第 9 章 LangGraph 条件边的思想雏形。

**预期输出**:

```
用户:我买的音箱用了三天没声音了,你们这是卖假货吧!
  -> 识别为[投诉],回复:非常抱歉给您带来了不好的体验,您的心情我完全理解...
```

## 5. 常见坑

1. **温度忘了调 0** —— 抽取/分类任务 `temperature=0`,否则同一输入两次结果不同,测试没法写;
2. **schema 太复杂一次抽** —— 字段超过 10 个准确率明显下降;拆成两步抽取,或砍掉低价值字段;
3. **description 写得太玄** —— "name: 姓名"就好,不要写"用户之代号";
4. **拿不到就编** —— 必须给"未提及"留出口:`None` 默认值 + description 里写明"未提及则为 null";
5. **嵌套太深** —— 三层以上嵌套模型容易触发格式错误,扁平化或分步处理;
6. **把校验异常吞掉** —— Pydantic 校验失败抛异常是**特性**:说明模型没按 schema 出牌,应记录并重试,而不是 try 过了事。

## 6. 小结与练习

`with_structured_output` = schema 即提示词 + 输出即对象 + 校验自动化。
组合 batch(并发)、Literal(枚举)、嵌套模型(复杂结构),足以覆盖绝大多数"模型输出进程序"的场景。
