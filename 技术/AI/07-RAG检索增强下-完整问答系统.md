# 第 7 章 · RAG(下):完整的检索问答系统

> 本章目标:把第 6 章的 Retriever 接上 LLM,组装出三个递进的 RAG 应用:
> 基础 RAG 链 → 带引用来源 → 多轮对话式 RAG(会话+检索的组合拳)。
>
> 对应 demo:`rag_chain.py`、`rag_with_sources.py`、`conversational_rag.py`

---

## 1. Demo 7-1 · rag_chain.py:RAG 链骨架(本教程最重要的 20 行)

```python
rag_chain = (
    RunnablePassthrough.assign(
        context=itemgetter("question") | retriever | RunnableLambda(format_docs)
    )
    | prompt          # 模板:{context} + {question}
    | llm
    | StrOutputParser()
)
```

逐环拆解(第 4 章的 LCEL 知识在此集中兑现):

1. `itemgetter("question") | retriever | RunnableLambda(format_docs)` —— 一条**子链**:
   从输入字典取出问题 → 检索 → 把 Document 列表拼成一段文本;
2. `RunnablePassthrough.assign(context=子链)` —— 关键组合拳:
   **保留原输入的 `question`**,同时给输入字典**新增** `context` 键。
   于是进入模板时,`{question}` 和 `{context}` 都有了;
3. 后半段就是普通的 `prompt | llm | parser`。

**为什么 `RunnablePassthrough.assign` 如此常用**:RAG 链的模板永远同时需要
"原始问题"和"检索结果",`assign` 正好做"增量注入"。这个模式请背下来,
第 8、9 章还会反复出现。

### 防幻觉的关键句

system 提示词里的这句**不是客套话**,是 RAG 的安全带:

> "仅根据参考资料回答;资料中没有的信息,直接回答'资料中未提及',不要编造。"

demo 第三个问题"公司明年的股价目标是多少?"就是来验证安全带的——资料里没有,
模型应老实说"未提及",而不是现场编一个股价目标。**预期输出**:

```
Q:年假最多可以有多少天?
A:根据员工手册,工作满 10 年的员工享有最多 12 天带薪年假。

Q:公司明年的股价目标是多少?
A:资料中未提及。
```

## 2. Demo 7-2 · rag_with_sources.py:可追溯的答案

企业落地 RAG 的第一道验收标准往往是:**答案能不能标注出处?**(HR 不敢直接采信一个黑盒答案。)

做法:

1. 入库前给 metadata 加上可读的 `title`(文件名);
2. 检索后给每段资料加 `[编号]` 前缀,连同文档名一起塞进提示词;
3. 提示词要求:正文用 `[编号]` 标注 + 末尾列出引用清单。

```python
hits = db.similarity_search(question, k=3)
context = "\n\n".join(
    f"[{i}] (文档:{h.metadata.get('title')}) {h.page_content}"
    for i, h in enumerate(hits, 1)
)
```

**预期输出**:

```
Q:出差住宿标准是多少?
A:一线城市 500 元/晚,其他城市 350 元/晚 [1]。
引用:[1] employee_handbook.md
```

进阶方向:拿模型的结构化输出(第 3 章)返回 `{answer, cited_ids}`,
前端就能把编号做成可点击跳转的角标(答案角落的小标注),用户信任度显著提升。

## 3. Demo 7-3 · conversational_rag.py:多轮对话式 RAG

### 3.1 问题:代词毁掉检索

多轮对话里,用户第二问往往是:

```
用户:年假有几天?      -> 检索"年假有几天" ✅
用户:那病假呢?        -> 直接拿"那病假呢?"去检索 ❌
                          向量库里没有一句话讲"那",检索必然失败
```

第 5 章的记忆方案解决了"模型知道上文",但**检索器不知道上文**——它是个无状态的向量匹配器。

### 3.2 方案:先改写查询,再检索

两阶段链:

```
对话历史 + 新问题 ──> [改写链:LLM] ──> 独立完整的新查询 ──> [检索] ──> [生成链] ──> 回答
```

改写链把"那病假呢?"改写成"公司的病假制度是什么?"(demo 运行时会打印改写结果,
建议盯着看模型改得对不对)。之后检索、生成都回到 7-1 的骨架,历史维护用第 5 章的手动方案。

这个"**改写 → 检索 → 生成**"的三段式,就是对话式 RAG 的标准形态。
它也让你第一次看到:**多个 LLM 调用在一条业务流程里各司其职**(改写一次、生成一次)。
当流程继续膨胀(分类、路由、并行……),手写胶水代码就不划算了——第 9 章的 LangGraph 登场。

## 4. 生产级 RAG 的进阶路线图

本教程 demo 已覆盖主干,真实系统通常还要做(按优先级):

| 方向 | 手段 | 一句话说明 |
|------|------|-----------|
| 检索质量 | 混合检索 | 向量(按意思)+ 关键词(按字面)两路一起找再融合,对付型号、人名等精确词 |
| 检索质量 | 重排(Rerank) | 召回 top20 后用重排模型精选 top3,准确率提升最明显的一招 |
| 查询侧 | 查询改写/扩展 | 本章 7-3 已做;进一步可让模型从多角度生成多个查询 |
| 数据侧 | 文档结构化切分 | markdown 按标题切、表格单独处理、图片走多模态(能同时理解文字和图片的模型) |
| 评估 | 检索命中率 + 答案忠实度 | 没有评估的 RAG 无法调参,见第 10 章 LangSmith |

## 5. 常见坑

1. **每次运行都重新建库** —— demo 为自包含每次重建;生产必须持久化(`persist_directory`)并在文档变更时增量更新;
2. **`format_docs` 里没截断** —— k 个块全量塞入,块多时超出上下文;给 context 设长度上限;
3. **提示词没写"仅根据资料回答"** —— 模型自由发挥,幻觉率飙升;
4. **改写链也把幻觉带进来** —— 改写模型可能脑补用户意图,改写结果要人工抽检;
5. **检索了但答案引用错编号** —— 模型偶尔标错,用结构化输出约束引用字段可显著缓解;
6. **所有文档一视同仁** —— 权限差异(部门文档混检)是企业级事故重灾区,用 metadata 过滤兜底。

## 6. 小结与练习

RAG 骨架 = `RunnablePassthrough.assign(context=retriever子链) | prompt | llm | parser`。
三个能力台阶:能答 → 能溯源 → 能多轮。

**练习**:

1. 把 7-1 的 k 改成 1 和 8,对比答案质量与耗时变化;
2. 给 7-2 加"未检索到相关资料时不回答"的逻辑(检索结果为空时直接短路返回固定话术);
3. 把 7-3 的历史换成第 5 章的 trim_messages 裁剪方案,防止长会话撑爆改写链。
