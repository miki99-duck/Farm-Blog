# 第10章 虚拟线程（Virtual Threads）原理

> 学习定位：Java 21 之后最重要的语言级变化，Spring Boot 4 默认开启。
> 本章讲透机理：为什么需要它、JVM 怎么实现它、有哪些坑、什么时候用它。
> 面试问法：虚拟线程是什么/怎么实现/和线程池什么关系/pinning 怎么避免。

## 1. 先看老问题：平台线程为什么不够用

传统 Java 并发模型里，一个线程 = 一个操作系统线程（1:1 模型）：

- 栈空间：默认约 1MB（Xss 512k~1M），是固定分配的
- 创建成本：毫秒级（要系统调用、分配内核栈与 TCB）
- 切换成本：涉及内核态切换，耗时微秒级 ~ 微妙级不等
- 硬上限：一台 2C4G 的机器，撑到几千个线程就开始不稳定

于是出现"线程饥饿"：后端接一个 HTTP 请求 → 需要一个线程 → 线程被阻塞等待
JDBC/Kafka/远程调用（I/O 密集场景，线程 90%+ 时间在等） → 线程池 200 个很快占满 →
后面的请求排队超时。

传统解法是"异步化"：NIO + 回调 / CompletableFuture / WebFlux。
代价：代码反人类——本来顺序的流程被拆成回调链，调试困难，心智负担大。

一句话总结：**线程是稀缺资源，但我们却用它去"等待"——太浪费了。**

## 2. 虚拟线程是什么

虚拟线程（Project Loom 的成果，Java 21 正式发布）：

- 由 **JVM 管理**的轻量级线程，不直接对应任何 OS 线程（M:N 模型）
- 本质是一个 Java 对象：调度状态 + 在堆上的可增长栈
- 跑在"载体线程"（Carrier Thread = 平台线程）上，多个虚拟线程共享少量载体线程
- 创建成本微秒级，栈从几 KB 起步按需增长
- 数量：不受 OS 限制，单进程几十万、上百万个都行

和 Go goroutine 几乎同一思想：**用户态调度**。Go 由 runtime 调度 goroutine，
Java 由 JVM 调度虚拟线程。区别是虚拟线程完全复用 java.lang.Thread API，
老代码几乎不用改。

## 3. 核心原理：Mount / Unmount（挂载与卸载）

这是理解一切的关键。虚拟线程的生命周期是"反复挂到载体线程上干活，阻塞时卸下来"：

```
载体线程（平台线程，数量 = CPU 核数，由 ForkJoinPool 调度器管理）
   │
   ├── 挂载(mount)：把虚拟线程 A 的栈"装"到载体线程上运行业务代码
   │
   ├── A 执行到阻塞点（如 socket.read()、Thread.sleep()、加锁等待）
   │
   ├── 卸载(unmount)：A 的栈帧保存回堆内存，载体线程被释放
   │       ↑ 这一步对内核完全无感 —— 载体线程并没有阻塞！
   │
   ├── 载体线程立刻挂载虚拟线程 B 继续跑
   │
   └── A 的 I/O 就绪后 → JVM 把它放回调度队列 → 抢到载体线程再挂载继续执行
```

关键点分解：

1. **阻塞不是真阻塞**：虚拟线程"阻塞"时，底层载体线程没有进入内核阻塞状态，
   而是 JVM 把虚拟线程的上下文（栈、寄存器状态）保存起来，载体线程转身去干别的。
2. **谁改造了阻塞点**：JDK 内的阻塞 API（InputStream/OutputStream、Socket、
   Thread.sleep、Object.wait、ReentrantLock、Semaphore 等）都重新实现为"可让出"，
   在阻塞时触发 unmount。
3. **调度器**：默认是一个 ForkJoinPool，parallelism = CPU 核数（可调
   -Djdk.virtualThreadScheduler.parallelism）。也就是说**并行计算能力不增加**，
   增加的是"同时等待的能力"。
4. **栈**：在堆上动态分配，按需增长/收缩，不占固定 1MB。

```java
// 创建虚拟线程的三种方式（等价的）
Thread t1 = Thread.ofVirtual().start(() -> doIo());       // 方式1
try (ExecutorService es = Executors.newVirtualThreadPerTaskExecutor()) {
    es.submit(() -> doIo());                              // 方式2（推荐，每任务一个虚拟线程）
}
// 方式3：Thread.ofVirtual().name("iot-").unstarted(r).start();
```

为什么"每任务一个虚拟线程"没问题：虚拟线程创建太便宜了，不需要池化。
**线程池的意义（复用昂贵资源）在虚拟线程身上消失了。**

## 4. 一个直观对比：同样是 10 万个 I/O 任务

```java
// 场景：10 万个耗时 100ms 的模拟阻塞任务（如调第三方接口、查库）

// ① 固定线程池 8 线程：10万 × 100ms ÷ 8 ≈ 21 分钟
try (ExecutorService es = Executors.newFixedThreadPool(8)) {
    for (int i = 0; i < 100_000; i++) {
        es.submit(() -> Thread.sleep(100));   // 模拟阻塞 I/O
    }
}

// ② 虚拟线程：10万 × 100ms ÷ (核数 但并行让出) ≈ 100 秒级（取决于 I/O 并发度）
try (ExecutorService es = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        es.submit(() -> Thread.sleep(100));   // sleep 时虚拟线程让出载体线程
    }
}
```

结论：**I/O 密集场景吞吐提升是数量级的；CPU 密集场景没有提升**（虚拟线程不增加算力）。

## 5. 两个必知的坑

### 5.1 Pinning（钉住载体线程）—— synchronized 的坑

问题：虚拟线程执行到 synchronized 块内部并发生阻塞时，**不能 unmount**，
把载体线程"钉死"占住，载体线程干不了别的 → 等于退化回平台线程。

根因：synchronized 编译成 monitorenter/monitorexit，走的是 JVM 原生监视器
（native monitor + 阻塞原语），JDK 没有把这条路径改造成可让出的。
（JDK 24 的 JEP 491 已解决"同步增删"性能问题；pin 场景后续版本也在持续改进，
但**面试标准答案仍是：避免 synchronized 里长时间阻塞，用 ReentrantLock**。）

```java
// 会 pin：synchronized 块内阻塞，载体线程被钉住
public synchronized void handle(String msg) {
    Thread.sleep(100);   // ❌ 这里虚拟线程无法让出，载体线程被占
}

// 不 pin：用 ReentrantLock 等 j.u.c 锁（JDK 已改造为可让出）
private final Lock lock = new ReentrantLock();
public void handle(String msg) {
    lock.lock();
    try {
        Thread.sleep(100);   // ✅ 阻塞时让出，不占载体线程
    } finally {
        lock.unlock();
    }
}
```

### 5.2 ThreadLocal 放大 —— 数据隔离的坑

问题：每个虚拟线程都是独立的 Thread 实例，都持有自己的 ThreadLocal 地图。
虚拟线程数量巨大（几十万），若每个都往 ThreadLocal 塞数据（如 traceId、
SecurityContext），内存会放大几十万倍。

另一面：共享载体线程时，把数据写进**载体线程的 ThreadLocal** 会造成串味
（一个载体线程跑多个虚拟线程都读到同一个值）。Spring 已做适配，但自己写要小心。

```java
// 虚拟线程场景，避免把大对象/长生命周期数据塞 ThreadLocal
// 新代码用 ScopedValue（Java 24 正式）替代：
private static final ScopedValue<String> TRACE_ID = ScopedValue.newInstance();

String result = ScopedValue.where(TRACE_ID, "trace-123")
        .call(() -> doIo());           // 只有这个调用链能看到，自动清理，不泄漏
```

结论：**传递上下文用参数或 ScopedValue，别依赖 ThreadLocal。**

## 6. 什么时候用虚拟线程（决策表）

| 场景 | 用虚拟线程？ | 说明 |
|------|------------|------|
| HTTP 接口里查库/调第三方（I/O 密集） | ✅ | Boot 4 默认，零改动 |
| 批量跑批：给 10 万设备发指令 | ✅ | 每任务一个虚拟线程，天然高并发 |
| Kafka 多分区消费 | ✅ | 每个消息/任务一个虚拟线程 |
| CPU 密集计算（加解密、压缩、图像处理） | ❌ | 无并行收益，用核数的平台线程池 |
| 需要并发限流的场景 | ⚠️ | 线程数不再是你限流的手段，改用 Semaphore/队列上限 |
| 需要分布式锁/DB 幂等的任务 | ⚠️ | 虚拟线程解决不了业务幂等与死锁问题 |

要点：
- 虚拟线程**能**解决的：线程数量瓶颈、线程池线程饥饿。
- 虚拟线程**不能**解决的：CPU 并行度、业务幂等、死锁、分布式一致性问题。
- 限流思路要变：以前"线程池 200 就是并发上限"，现在线程不限了，
  要限制的是"对下游/数据库的并发压力"，用 Semaphore 或信号量控制。

## 7. Spring 里怎么用（接第9章）

```yaml
# Boot 3.2 / 3.5：显式开启
spring:
  threads:
    virtual:
      enabled: true

# Boot 4.0：Java 21+ 默认开启，无需配置
```

生效范围：内嵌 Tomcat/Jetty 的请求处理线程 → 虚拟线程执行器；
Spring Boot 4 还支持虚拟线程的 @Async 与定时任务执行器。

```java
// Boot 4 / Spring 6.1：让 @Async 也用虚拟线程
@Bean
AsyncTaskExecutor applicationTaskExecutor() {
    return new SimpleAsyncTaskExecutor(Thread.ofVirtual().name("async-").factory());
}
```

提醒：JDBC 连接池（HikariCP）有上限（默认 10）——虚拟线程让"等连接"变得不再占线程，
但连接池本身仍是瓶颈，所以**数据库连接池大小要按业务量重新评估**，别只用默认值。

## 8. 面试追问链（自测）

- Q：虚拟线程和平台线程什么关系？
  A：M:N——JVM 把大量虚拟线程调度到少量（=CPU 核数）载体线程上。
- Q：虚拟线程为什么提高吞吐？
  A：阻塞时让出载体线程，线程不再浪费在"等待"上，同时挂起等待的任务数量不再受线程数限制。
- Q：虚拟线程加 CPU 并行吗？
  A：不加。并行度由载体线程决定（核数），虚拟线程只增加并发/等待能力。
- Q：pinning 是什么？
  A：synchronized 块内阻塞时虚拟线程无法 unmount，载体线程被钉住。用 ReentrantLock 避免。
- Q：虚拟线程有栈吗，占多少内存？
  A：有，在堆上按需增长，几十 KB 起，不像平台线程固定 1MB。
- Q：那我还需要线程池吗？
  A：固定线程池跑 I/O 的意义消失了；CPU 密集场景仍用核数匹配的平台线程池。
- Q：和 goroutine 比？
  A：同一思想（用户态调度），Go runtime vs JVM 调度，Java 兼容 Thread API，迁移成本低。

## 9. 一句话总结

**虚拟线程 = JVM 把"等 I/O"变得几乎免费：阻塞即卸载、就绪再挂载，
让同步代码拿到异步的吞吐；代价是别在 synchronized 里阻塞、别滥用 ThreadLocal。**
