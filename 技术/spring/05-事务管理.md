# 第5章 事务管理

> 面试定位：性价比之王。@Transactional 怎么生效、哪些场景失效、传播行为怎么选，
> 是 Java 后端面试命中率最高的一集。本章学完，事务问题基本全覆盖。

## 5.1 一句话讲清

**@Transactional 不碰任何数据库代码，它只是给目标方法挂了一个 AOP 切面：
方法执行前由 TransactionInterceptor 开启事务（连接 setAutoCommit(false)），
方法正常返回就 commit，抛出 RuntimeException/Error 就 rollback。**

## 5.2 声明式事务原理：一条完整调用链

```
@Transactional 注解
  → 被 AOP 切面拦截（TransactionInterceptor，本质是一个 Advice）
  → invokeWithinTransaction
  → PlatformTransactionManager（接口）
      ├─ DataSourceTransactionManager（单数据源默认实现）
      ├─ JpaTransactionManager / HibernateTransactionManager
      └─ 多数据源 → 需要 JTA / 分布式事务方案
  → 拿到数据库连接 Connection
  → setAutoCommit(false) → 执行业务 SQL
  → 提交：connection.commit()  /  回滚：connection.rollback()
```

代码1：关键链路摘录（概念版）

```java
// TransactionInterceptor 核心逻辑（概念版）
public Object invoke(MethodInvocation invocation) throws Throwable {
    TransactionInfo txInfo = createTransactionIfNecessary(transactionManager, ...); // 开事务
    try {
        Object retVal = invocation.proceed();      // 执行目标方法（业务 SQL）
        commitTransactionAfterReturning(txInfo);   // 成功 → 提交
        return retVal;
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);  // 异常 → 按规则回滚
        throw ex;
    }
}
```

**和 AOP 的关系**：@Transactional 生效的前提 = 方法被代理（外部调用）。
上一章 4.5 的自调用失效，在事务场景就是"同类里 this 调 @Transactional 方法 → 事务失效"。

## 5.3 传播行为：7 种怎么记

图9 传播行为决策树：

```
当前方法要不要加入事务？
├─ 有事务？
│   ├─ REQUIRED       → 加入当前事务（默认，最常用）✅
│   ├─ REQUIRES_NEW   → 挂起当前事务，开全新事务（新事务独立提交/回滚）✅
│   ├─ NESTED         → 嵌套事务（回滚到保存点，部分回滚）⚠️
│   ├─ SUPPORTS       → 有就用，没有就算了
│   ├─ MANDATORY      → 必须有，没有抛异常
│   ├─ NOT_SUPPORTED  → 挂起事务，以非事务方式执行
│   └─ NEVER          → 必须没有事务，有就抛异常
└─ 没事务？
    ├─ REQUIRED / REQUIRES_NEW / NESTED → 直接新建事务
    └─ SUPPORTS / NOT_SUPPORTED / NEVER / MANDATORY → 非事务或抛异常
```

面试必背三兄弟对比：

| 传播行为 | 外层有事务时 | 典型场景 |
|---------|-------------|----------|
| REQUIRED | 加入外层，一起提交/回滚 | 普通业务方法（默认） |
| REQUIRES_NEW | 挂起外层，各自独立 | 记日志必须成功，不能随业务回滚 |
| NESTED | 内层失败只回滚内层（保存点） | 批量导入，单条失败不影响整体（需数据库支持保存点） |

代码2：REQUIRES_NEW 演示"日志不回滚"

```java
@Service
public class OrderService {
    @Autowired private LogService logService;

    @Transactional
    public void createOrder() {
        // ... 下单 SQL
        logService.writeLog("创建订单");  // REQUIRES_NEW：独立事务
        // ... 若这里抛异常回滚，writeLog 已提交，日志仍保留
    }
}

@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void writeLog(String msg) { ... }
}
```

追问：REQUIRED 内层方法抛异常、外层 try-catch 能继续提交吗？
答：不能。REQUIRED 共用一个事务，内层抛 RuntimeException 已把事务标记为 rollback-only，
外层即使 catch 住，提交时也会抛 UnexpectedRollbackException。这就是经典的
"catch 了异常事务还是回滚"坑。要局部隔离就用 REQUIRES_NEW 或 NESTED。

## 5.4 事务失效场景大全（必考，背全）

| # | 失效场景 | 原因 |
|---|---------|------|
| 1 | 同类内 this 调用 | 不走代理（见 4.5） |
| 2 | 异常被 try-catch 吞掉 | 没抛出去，拦截器以为成功，commit |
| 3 | 抛的是检查异常（如 IOException） | 默认只回滚 RuntimeException/Error |
| 4 | 方法不是 public | 默认 proxy 模式只能代理 public 方法（CGLIB 也拦不住非 public 调用） |
| 5 | 类没被 Spring 管理（没加 @Service 等） | 没有代理，注解被忽略 |
| 6 | final 类 / final 方法 | CGLIB 无法继承/重写 |
| 7 | 数据库引擎不支持事务 | 如 MyISAM（InnoDB 才支持） |
| 8 | 多线程调用 | 新线程没有绑定原事务的连接 |
| 9 | propagation = NOT_SUPPORTED | 明确指定不启用事务 |
| 10 | 多数据源 | @Transactional 只作用于事务管理器绑定的那个数据源 |

代码3：两种最常见失效的修复（对照）

```java
// 失效1：异常被吞
@Transactional
public void save() {
    try {
        dao.insert(a);
        dao.insert(b);
    } catch (Exception e) {
        log.error("忽略异常", e);   // ❌ 异常没抛出去，insert(a) 也提交了
    }
}

// 修复：让事务感知异常
@Transactional(rollbackFor = Exception.class)
public void save() {
    try {
        dao.insert(a);
        dao.insert(b);
    } catch (Exception e) {
        log.error("回滚", e);
        throw new RuntimeException("保存失败", e);  // ✅ 抛出去，触发回滚
    }
}

// 失效2：默认不回滚检查异常
@Transactional
public void export() throws IOException {
    // ... 抛 IOException 时不会回滚（检查异常默认不回滚）
}
// 修复：@Transactional(rollbackFor = Exception.class) 显式声明
```

面试讲法：**"默认只回滚 RuntimeException 和 Error，因为检查异常代表业务上的可恢复失败，
框架不敢替你回滚；要回滚就显式 rollbackFor。"**

## 5.5 隔离级别速记（低频，知道即可）

| 级别 | 现象 | 说明 |
|------|------|------|
| READ_UNCOMMITTED | 脏读 | 最低，几乎不用 |
| READ_COMMITTED | 不可重复读 | Oracle 默认 |
| REPEATABLE_READ | 幻读 | MySQL 默认（InnoDB 用 MVCC 基本避免幻读） |
| SERIALIZABLE | 全部避免 | 性能最低 |

## 5.6 结合简历项目（华润 IoT 平台）

- **多数据源是重点加分项**：你的项目 MySQL/PostgreSQL 双数据源，
  面试问"多数据源事务怎么处理"，答案是三层：
  ① 每个数据源配各自的 PlatformTransactionManager；
  ② @Transactional 默认只管 primary 那个（DataSourceTransactionManager 只能操作它绑定的连接）；
  ③ 跨数据源一致性需要 JTA（Atomikos）或分布式事务（Seata），或改造成"最终一致 + 本地消息表/重试"。
- IoT 场景典型问题：Kafka 消费 → 落库，消费成功但事务回滚 → 丢数据。
  解法：先落库（本地事务）再 ack，或用"事务消息/本地消息表"保证最终一致。
  面试讲这个 = 从"会用事务"上升到"懂分布式事务"，拉开差距。
- IotPersistenceService 批量入库：单批包在一个事务里，异常整批回滚并交给 Kafka 重试，
  幂等靠 msgId（mid）去重 —— 这就是事务 + 幂等双保险，可以直接讲。

## 本章小结

- @Transactional = AOP 切面，TransactionInterceptor 开/提交/回滚。
- 默认回滚 RuntimeException/Error，检查异常要 rollbackFor。
- REQUIRED 同生共死，REQUIRES_NEW 独立，NESTED 部分回滚。
- 失效场景背全 10 条，前 6 条面试高频。
- 多数据源 = 每源一个事务管理器，跨源一致性要 JTA/Seata/最终一致。
