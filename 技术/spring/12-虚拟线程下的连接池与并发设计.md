# 第12章 虚拟线程下的连接池与并发设计

> 主题：虚拟线程把"线程数"这个瓶颈取消了，但**下游资源（数据库连接、第三方接口
> 配额、Redis 连接、Kafka 分区）没有变多**。真正的瓶颈转移了——从"线程"转移到
> "连接/配额"。本章讲清楚新模型下怎么设计连接池与限流，否则虚拟线程会把你打爆。

## 1. 问题模型：瓶颈从线程转移到下游

升级前（平台线程）：
```
线程池 200 上限 ◄── 这本身就是一道"天然限流闸门"
   └─ 超出的请求排队 → 客户端超时 → 失败可见
```

升级后（虚拟线程，Boot 4 默认）：
```
虚拟线程无上限 ◄── 闸门消失！
   ├─ 1 万个请求 = 1 万虚拟线程，全部同时去查数据库
   ├─ HikariCP 默认 10 个连接 → 9990 个虚拟线程在队列里等连接
   ├─ 数据库被打满（或崩溃），连接超时连锁失败
   └─ 问题：虚拟线程"看起来都成功了"，实际卡死在等资源
```

一句话：**虚拟线程让应用"不再缺线程"，但数据库/WAF/下游 RPC 该缺还是缺。
以前靠线程池限流，现在必须主动设计限流。**

## 2. 连接池设计：按"下游真实能力"配置，不按并发配置

### 2.1 核心公式（Little's Law）

             并发需要的连接数 ≈ 单请求占用连接时间 × 每秒请求数
             (In-Flight)      =    W（响应时间）      ×   λ（吞吐）

- 例：单条 SQL 平均 50ms，目标吞吐 500 QPS：
  需要并发 ≈ 0.05s × 500 = 25 个连接。
- 例：慢查询 500ms、吞吐 200 QPS：0.5 × 200 = 100 个连接——连接池要放大，
  否则等连接就是新的瓶颈。

### 2.2 HikariCP 配置原则

```yaml
# 之前：拍脑袋填 10/20/50 —— 现在按公式填
spring:
  datasource:
    hikari:
      maximum-pool-size: 30       # ← W × λ 算出，再留 20% 余量
      minimum-idle: 5             # 空闲保活，应对突发
      connection-timeout: 3000    # 拿不到连接最多等 3 秒，别无限等
      max-lifetime: 600000        # 10 分钟，比 MySQL wait_timeout 短
      connection-test-query: SELECT 1
```

注意三个反直觉点：
1. **连接池大小不是越大越好**：MySQL 8 上 50~100 连接往往比 10 连接吞吐更低
   （锁竞争、上下文切换）。连接数要贴下游真实吞吐，不是贴并发。
2. **connection-timeout 必须设**：虚拟线程等连接是"软阻塞"，无限等 =
   请求全部悬挂，链路上游也超时，雪崩。设置超时让失败快、可重试。
3. **空闲连接要回收**：虚拟线程并发波动大，max-lifetime 和 minimum-idle 配合，
   避免连接池被瞬间打满后长期占着。

### 2.3 面向连接池的三种方案选择

| 方案 | 做法 | 适用 |
|------|------|------|
| A. 少量大连接池 | 按公式算，够用即可 | 单库、SQL 稳定 |
| B. 读库分离 | 主库写 + 从库读，各配各的池 | 读多写少（报表、看板） |
| C. 队列削峰 | 请求入口限流/排队，超过容量直接 429 | 外部压力不可控（秒杀、批量导入） |

## 3. 限流设计：信号量代替"线程数"

虚拟线程世界里的核心心智模型：

> **线程数 = 并发执行能力（不限）；信号量 = 对某一下游并发压力的闸门（必须限）。**

```java
// 给"调用第三方燃气平台"这个下游单独配信号量
@Component
public class GasPlatformClient {
    private final Semaphore semaphore = new Semaphore(20); // 最多 20 路并发打下游

    public Result push(IotData data) {
        if (!semaphore.tryAcquire(2, TimeUnit.SECONDS)) {
            throw new BusyException("下游繁忙，稍后重试");   // 快速失败
        }
        try {
            return doHttpPush(data);   // 阻塞 HTTP，虚拟线程让出载体线程
        } finally {
            semaphore.release();
        }
    }
}
```

要点：
- 信号量对象是**被所有虚拟线程共享的**（单例），虚拟线程并发再多也撞同一个闸门。
- tryAcquire 带超时：拿不到就快速失败（可返回 429 / 走重试队列），别无限等。
- **每个下游配一个信号量**：数据库、第三方 API、Redis 各自独立限流。

限流层级（按优先级从高到低）：

```
① 入口限流：网关/Filter 层按 IP/用户/接口 限流（RateLimiter）
② 资源限流：信号量限定某下游并发（上面示例）
③ 队列削峰：需要保序/保证落库的（Kafka 天然就是队列，消费侧并发按需控制）
④ 数据库侧：连接池大小 + 慢查询治理（最终防线）
```

## 4. 常用组件在虚拟线程下的并发配置

### 4.1 JDBC（HikariCP）
- maximum-pool-size 按 2.2 公式配置；connection-timeout 必须设。
- 多数据源项目（你的 MySQL + PostgreSQL）：各配各的池，别共享连接。

### 4.2 HTTP 客户端（RestClient / HttpClient / OkHttp）
- JDK HttpClient 默认连接池无限制？——实际上连接复用有限（keep-alive），
  虚拟线程下大量并发 HTTP，要关注连接上限与超时。

```java
// JDK HttpClient：限制连接与超时
HttpClient httpClient = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))
        .executor(Executors.newVirtualThreadPerTaskExecutor())  // 发送/回调跑虚拟线程
        .build();
```

### 4.3 Redis（Lettuce / Jedis）
- Lettuce 本身基于 Netty 异步，虚拟线程下没大问题；Jedis 是线程安全共享一个连接池，
  按 Redis 单实例吞吐（约 10 万 QPS）配池即可，通常 50~100 连接足够。
- 注意：Redis 是内存操作，延迟微秒级，**连接占用极短**，池子不需要大。

### 4.4 Kafka 消费者
- 消费者并发 ≠ 线程数：受**分区数**约束（一个分区同一时刻只能被组里一个消费者消费）。
- 提升吞吐的正确姿势：加分区（扩容）+ 增加消费组里的消费者实例；
  单个消费者内用虚拟线程并行处理消息批次可以，但别幻想超过分区数。
- 你的场景（Kafka 批量落库）：单消费者拉批 → 批次内虚拟线程并行落库 →
  等全部完成再提交 offset —— 这就是"有序 + 并行 + 不丢"的典型设计。

```java
// 消费批次内并行落库（示意）
@KafkaListener(topics = "iot_north_data_collect")
public void onBatch(List<ConsumerRecord<String, String>> records) {
    try (ExecutorService vt = Executors.newVirtualThreadPerTaskExecutor()) {
        List<Future<?>> futures = records.stream()
                .map(r -> vt.submit(() -> persistence.save(r.value())))  // 每个一条虚拟线程
                .toList();
        for (Future<?> f : futures) f.get();   // 全部成功才提交 offset
    }
}
```

## 5. 反模式清单（线上常见的翻车姿势）

| 反模式 | 后果 |
|--------|------|
| 虚拟线程开启后连接池还是 10 | 高并发时 9990 个线程排队等连接，延迟爆炸 |
| connection-timeout 无限大 | 请求全部悬挂，上游全部超时，雪崩 |
| 无信号量直连第三方 | 第三方被你的并发打挂，RateLimit 403 刷屏 |
| 同步阻塞里用 synchronized | pinning，虚拟线程退化（见第10章 5.1） |
| 每个请求 new 一个连接 | 连接池形同虚设，数据库被连接的建立/销毁拖死 |
| 批量任务无限并发 | 数据库/下游被打爆，且无重试边界 |

## 6. 工程实践清单（升级后必做五件事）

1. 连接池按公式重配：maximum-pool-size = 响应时间 × 吞吐 + 20% 余量。
2. 所有 connection-timeout / read-timeout 显式设置（3 秒起步，按链路调）。
3. 给每个外部依赖（DB、第三方 API、Redis）配信号量限流，快速失败优先。
4. 监控 connection pending（HikariCP 的 Pending 指标）——**这个是新的核心告警指标**，
   替代原来的"线程池拒绝"告警：
   ```json
   // actuator 暴露（Boot 3+ 自动）
   hikaricp_connections_pending
   hikaricp_connections_timeout_total
   ```
5. 压测时**同时压吞吐和并发**：虚拟线程下并发加到 1 万，看的是数据库扛不扛得住，
   不是应用扛不扛得住。

## 7. 面试话术

- Q：虚拟线程这么好，直接全换上？→ "换线程模型很简单，难的是下游资源。
  虚拟线程消除了线程瓶颈，但连接池/限流要重新设计，否则是把压力原样推到数据库。"
- Q：连接池配置多少？→ 答 Little's Law 公式 + "贴数据库真实吞吐，不是贴并发，
  池太大反而更低"。
- Q：怎么防止虚拟线程打爆数据库？→ 三件套：连接池按公式限 + 信号量按下游限 +
  connection-timeout 快速失败。
- Q：Kafka 消费并发能靠虚拟线程提升吗？→ 受分区数约束，虚拟线程并行处理的是
  "批次内的任务"，分区才是吞吐上限。

## 8. 一句话总结

**虚拟线程没收"线程瓶颈"，却把压力转移到了连接与配额上——
新模型的并发设计 = 连接池按吞吐建模 + 信号量按下游隔离 + 超时快速失败 + 监控 pending。**
