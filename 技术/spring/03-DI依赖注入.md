# 第3章 DI 依赖注入

> 面试定位：中高频。必考 @Autowired 怎么工作的、候选歧义怎么处理、
> 三种注入方式选哪个。核心就一句话：**DI 是 IoC 的实现手段，干活的是 BeanPostProcessor。**

## 3.1 一句话讲清

**@Autowired 本身什么都不做，真正干活的是容器注册的一个 BeanPostProcessor——
AutowiredAnnotationBeanPostProcessor，它在 Bean 属性填充阶段（populateBean）扫描需要注入的字段/方法，
从容器里按类型找候选，把依赖"送进来"。**

## 3.2 @Autowired 的处理流程

图6 @Autowired 解析流程图（PlantUML）：

```
@startuml
start
:populateBean -> postProcessProperties;
:找到字段/方法上的 @Autowired;
:按类型获取候选 Bean (getBean);
if (候选数量?) then (0个)
  :required=true -> 抛异常 NoSuchBeanDefinitionException;
elseif (1个) then
  :直接注入;
else (多个)
  if (@Primary 存在?) then (是)
    :用 @Primary 指定的那个;
  else (否)
    if (@Qualifier 匹配?) then (是)
      :用 @Qualifier 指定的 name;
    else (否)
      :抛异常 NoUniqueBeanDefinitionException;
    endif
  endif
endif
:反射注入字段/调用 setter;
stop
@enduml
```

要点：
- 按**类型**找候选（byType），只有一个直接注入；多个按 @Primary → @Qualifier 依次裁决。
- @Resource（javax.annotation）和 @Autowired 不同：@Resource 先按**名称**（byName）匹配，
  名字找不到再按类型。面试对比时记：Autowired 类型优先，Resource 名称优先。
- 找不到候选且 required=false 时注入 null，不会抛异常。

## 3.3 三种注入方式对比（面试必背）

| 方式 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 构造器注入 | 依赖不可变(final)、必填性由编译期保证、**天然防循环依赖**、易单测 | 参数多时代码长 | ✅ 官方推荐 |
| Setter 注入 | 可选依赖、可后续改 | 对象可能处于"半初始化"状态 | 可选依赖时用 |
| 字段注入 | 代码最短 | 依赖隐藏、不可 final、难单测、**易踩循环依赖** | ⚠️ 避免（尤其新代码） |

代码1：三种方式对照

```java
// 1) 构造器注入（推荐）——final 保证不可变，单元测试直接 new 传参
@Service
public class IotService {
    private final IotPersistenceService persistence;
    public IotService(IotPersistenceService persistence) {  // 一个构造器，Spring 自动选它
        this.persistence = persistence;
    }
}

// 2) Setter 注入
@Service
public class SetterService {
    private KafkaTemplate<String, String> kafka;
    @Autowired
    public void setKafka(KafkaTemplate<String, String> kafka) { this.kafka = kafka; }
}

// 3) 字段注入（RuoYi 项目里最常见，面试要能指出它的缺点）
@Service
public class FieldService {
    @Autowired private IotPersistenceService persistence;  // 隐藏依赖，不好测，不推荐
}
```

追问：构造器注入为什么天然防循环依赖？
答：构造器注入要求在**实例化时**就把参数凑齐，而循环依赖解决机制需要对象"先实例化、后补依赖"。
构造器场景下两个 Bean 都没完成实例化，谁也等不到谁，直接抛 BeanCurrentlyInCreationException。

## 3.4 候选歧义：@Primary / @Qualifier / @Resource

代码2：多个候选的裁决

```java
// 有两个 DataSource 场景（你的项目正好是）：一个主一个从
@Bean @Primary                    // ① 默认挑它
public DataSource masterDataSource() { ... }

@Bean
public DataSource slaveDataSource() { ... }

@Service
public class ReportService {
    @Autowired
    @Qualifier("slaveDataSource") // ② 想要从库时用 Qualifier 点名
    private DataSource dataSource;
}
```

代码3：@Resource 按名称注入

```java
@Service
public class ConsumerService {
    // 按 bean 名称 "iotConsumer" 找；找不到再按类型
    @Resource(name = "iotConsumer")
    private KafkaConsumer iotConsumer;
}
```

追问链：
- Q：@Autowired 两个同类型 Bean 且都没有 @Primary？→ 抛 NoUniqueBeanDefinitionException。
- Q：能不能用 List<Xxx> 注入所有同类型 Bean？→ 可以，Spring 会按类型把全部候选装进 List，按 @Order 排序。
- Q：@Value 和 @Autowired 是什么关系？→ @Value 也是 AutowiredAnnotationBeanPostProcessor 处理的（处理 @Value 注解），注入的是属性值不是对象。

## 3.5 结合简历项目（华润 IoT 平台）

- 你的多数据源项目里，DataSource 有两个同类型 Bean，就靠 @Primary/@Qualifier 裁决，
  面试直接拿这个当例子讲"候选歧义"。
- MyBatis 的 Mapper 接口本身没有实现类，为什么 @Autowired 能注入？
  答：MyBatis 用 MapperFactoryBean（FactoryBean）注册，@Autowired 按类型解析时，
  会通过 FactoryBean 的 getObject() 拿到 Mapper 动态代理对象。
- Spring Boot 自己的自动配置里大量使用 @ConditionalOnMissingBean，本质也是
  "默认配置 + 允许用户覆盖"的候选裁决逻辑，留到第7章讲。

## 本章小结

- DI 的载体是 AutowiredAnnotationBeanPostProcessor，在 populateBean 阶段工作。
- 注入顺序：byType → 唯一则注入 → 歧义则 @Primary → @Qualifier → 否则抛异常。
- 推荐构造器注入：不可变、防循环依赖、好测试。
- @Resource 按名，@Autowired 按类型。
