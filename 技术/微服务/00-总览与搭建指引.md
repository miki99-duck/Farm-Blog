# 00 微服务四大难题：总览与搭建指引

> 一句话讲清:**微服务把单体拆开了,但同时带来四个经典难题——分布式事务、跨库分页、缓存一致性、消息可靠性。
> 本教程带你一步步从零搭出四个可运行的小项目,每个项目都是「反面教材 + 渐进解法 + 指标量化」的结构。**
> 读完你能做到:不看代码说出每个难题的根因和三种解法的取舍;能现场手写延迟双删和 outbox 的骨架。

## 一、四大难题是什么

```
单体应用（一个进程，一个数据库，一个缓存）
        │  拆分成
        ▼
微服务（多个进程，各自数据库，共享缓存）
        │
        ▼
┌────────────────────────────────────────────────────────────┐
│  难题一  分布式事务     一次下单要改 3 个库，失败了怎么回滚？   │
│  难题二  跨库分页查询    排序字段在 A 库，过滤字段在 B 库        │
│  难题三  缓存一致性      DB 和缓存双写，谁先写？读到的谁？      │
│  难题四  消息可靠性      业务落库了消息发不出，消费重复怎么办？   │
└────────────────────────────────────────────────────────────┘
```

**这四个难题有一个共同根因:一个「原子操作」被拆到了两个系统边界之外。**
单体的事务、SQL JOIN、缓存更新、本地方法调用,跨了服务边界就都不再原子。
所以解法也共享同一个思路:**要么缩小边界(把数据合并到一处),要么放弃强一致换最终一致(靠重试/补偿/去重兜底)。**

## 二、教程结构

| # | 章节 | 主题 | 方案数 | 对比指标 |
|---|------|------|--------|---------|
| 01 | 难题一 | 分布式事务(TCC) | 正向 + 3 个失败点 | `transactionStatus` |
| 02 | 难题二 | 跨库分页 + 条件过滤 | 3 个 | `remoteCalls` / `scannedRecords` |
| 03 | 难题三 | 缓存穿透/击穿/双写不一致 | 5 个(含 2 个错误顺序) | `dbCalls` / `cacheHits` / `staleReads` |
| 04 | 难题四 | 消息丢失 + 重复消费 | 3 个(A/B/C) | `lostMessages` / `duplicateProcessed` |

### 每个项目都是同一个教学套路

```
① 先搭一个「反面教材」—— 最朴素最直觉的写法（通常是错的）
② 跑起来，用指标看到它错在哪（不是嘴上说错，是数字告诉你）
③ 给渐进解法，每加一层防护解决一个具体问题
④ 同一个 API 入口切 solver 参数对比 —— 不用重启就能看差距
```

**为什么这套套路重要?** 分布式问题的可怕之处在于「本地怎么测都对,上线才炸」。
所以教学的重点不是背解法,而是**先亲手踩一遍坑,再理解解法为什么长那样**。

## 三、环境要求与统一约定

```
Java 17          # 4 个项目都用 17
Maven 3.6+
Spring Boot 3.3.5
```

### 项目布局

```
微服务四大难题/
├── pom.xml                  # 难题一:选课 TCC
├── src/                     # 难题一源码
├── cross-db-paging/         # 难题二:独立 Maven 工程
├── cache-consistency/       # 难题三:独立 Maven 工程
└── msg-reliability/         # 难题四:独立 Maven 工程
```

**四个工程互相独立,没有 `<modules>` 聚合**——故意这么设计:每个工程都能单独跑、单独讲,
不会因为某一个编译失败拖垮其他。代价是不能 `mvn install` 一条命令全跑,得进各自目录。

### 最重要的一个约定:全部用内存模拟,不依赖任何中间件

```
真实项目                      本教程
──────                      ──────
MySQL 库存表        →        ConcurrentHashMap
Redis 缓存          →        Map + 过期时间戳
Redis SETNX 分布式锁 →      ReentrantLock
RocketMQ / Kafka    →        内存 Map + 自增序号
Seata TCC 分支       →      本地方法调用
Canal/binlog → ES    →      Spring ApplicationEvent
```

**为什么这么设计?**
1. **零依赖启动**——`mvn test && java -jar` 就能跑,不需要先起 Redis、MQ、ES、MySQL。
   面试准备、离线环境、教学场景都能用。
2. **变量最少**——分布式问题本身就是多因素耦合,先排除掉中间件配置的干扰,聚焦问题本身。
3. **故障可注入**——内存实现可以随时造出「MQ 不可用」「缓存过期」「Try 失败」这些线上偶发场景,
   真实环境很难稳定复现。

**代价(必须说清楚):** 内存模拟**不体现**真实的网络延迟、中间件本身的语义差异、
以及跨机器的故障模式(比如网络分区)。学完四章后,真实接入 Redis/RocketMQ 时的细节差异要单独补。
每章我都会标出「真实场景对应什么」。

## 四、指标对比法:怎么看出方案差距

**这是四个项目共用的核心教学手法。** 每个项目都在基础设施层埋了计数器,通过 `/metrics` 端点暴露:

```java
// 难题三:每次数据库访问都计数
public Integer findStock(String productId) {
    dbCalls.incrementAndGet();     // ← 计数点
    return stocks.get(productId);
}
```

**为什么要埋指标?** 分布式方案的优劣**通常不能靠看代码判断,只能靠数字判断**。
比如「聚合查询 vs 宽表」,不看指标你只会觉得「都是查一次啊」;
看了指标才发现:聚合是 **10001 次**跨服务调用,宽表是 **1 次**。

**指标的可信度取决于口径定义。** 每个项目的指标都有一个「最容易算错」的地方,
我会在各章专门指出(比如难题四的 `lostMessages` 不能用 `sent - delivered` 推导)。

## 五、学习路径建议

```
第 1 天  难题一 TCC          —— 建立"分布式事务 = 编排 + 补偿"的直觉
第 2 天  难题二 跨库分页      —— 理解"数据放哪"是设计问题,不是技术问题
第 3 天  难题三 缓存一致性    —— 最复杂,方案最多,重点看两个错误顺序的窗口
第 4 天  难题四 消息可靠性    —— outbox + 幂等,面试最高频
```

也可以按面试优先级倒着学:**难题三 + 难题四是最高频的追问区**(缓存一致性几乎必问,
消息可靠投递是加分项),难题一考察分布式事务理解,难题二考察架构设计取舍。

## 七、代码风格约定(读代码前先知道)

| 约定 | 说明 |
|------|------|
| `record` 定义 DTO | Java 17 语法,替代手写 getter/setter,天然不可变 |
| 构造器注入 | 不用 `@Autowired` 字段注入,便于测试和不可变 |
| 中文 Javadoc | 每个类和方法都有注释,注释写「为什么」而不是「是什么」 |
| `Solver` 枚举 | 难题二/三统一用枚举分发方案,同一个 API 切参数对比 |
| 内存 Map 加 `ConcurrentHashMap` | 模拟并发环境,避免 HashMap 的并发坑 |
| 指标用 `AtomicInteger` | 计数在并发下也要准确 |

**一个要提前说的差异:** 难题一(根目录)的 `EnrollmentOrchestrator` 用 `new` 创建服务、没有 Spring 注入,
也没有 Javadoc;难题二三四都是标准的 Spring 构造器注入 + 中文 Javadoc。
读难题一时如果困惑「怎么不像 Spring 风格」,这是历史原因,不是刻意教学点。
