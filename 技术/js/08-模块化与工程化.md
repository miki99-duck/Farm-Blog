# 第8章 模块化与工程化（ES Module / npm / RuoYi 工程结构）

> 一句话讲清：**JS 从"一堆 script 标签谁都能用谁"进化到"每个文件一个模块、按需导入"；
> npm 管依赖（≈Maven），webpack/vite 打包（≈Maven 插件在构建期做事的角色）。
> RuoYi-Vue 用的是 webpack（Vue CLI），看懂它的目录就是看懂你的项目。**
> Java 对照：ES Module ≈ package/import；npm ≈ Maven 仓库；node_modules ≈ Maven 本地仓库；
> package.json ≈ pom.xml。

## 8.1 为什么需要模块化：历史的必然

```html
<!-- 远古时代：多个 script 按顺序加载，全部变量进全局 -->
<script src="a.js"></script>
<script src="b.js"></script>
<!-- 问题：a.js 里定义了什么 b.js 全知道；命名冲突、依赖顺序不可控 -->
```

模块化解决三件事：**作用域隔离（每个文件独立）、显式依赖（import 声明）、
按需加载（用多少引多少）。**

## 8.2 ES Module：现代标准写法

```js
// 导出：export / export default
// utils/format.js
export function formatDate(d) { ... }        // 命名导出（可多个）
export const PAGE_SIZE = 10;
export default function main() { ... }       // 默认导出（一个文件一个）

// 导入：import
// main.js
import { formatDate, PAGE_SIZE } from '@/utils/format';   // 命名导入
import main from '@/utils/format';                        // 默认导入
import * as utils from '@/utils/format';                  // 全部（命名空间）
```

关键规则（面试可能问）：
- 一个文件可有多个**命名导出** + 最多一个**默认导出**；
- import 的变量是**只读引用**（不能重新赋值）；
- import 会**提升**到文件顶部（写在后面也行）；
- 循环导入会出问题（尽量避免 A↔B 互相 import）。

RuoYi 里 `@/` 是什么：webpack 配置的别名，`@/` = `src/`，所以
`import request from '@/utils/request'` = `src/utils/request.js`。

## 8.3 npm：依赖管理（横向对照 Maven）

```bash
npm init -y                    # 生成 package.json（≈pom.xml）
npm install axios              # 安装依赖（写入 dependencies）
npm install -D sass            # 开发依赖（-D ≈ scope=provided）
npm run dev                    # 开发命令（脚本在 package.json scripts）
npm run build                  # 构建
```

package.json 核心字段：

```json
{
  "name": "ruoyi-ui",
  "version": "3.8.0",
  "scripts": {
    "dev": "vue-cli-service serve",        // 开发服务器
    "build:prod": "vue-cli-service build", // 打生产包
    "lint": "vue-cli-service lint"         // 代码检查
  },
  "dependencies": {                        // 运行依赖（≈compile）
    "axios": "^1.4.0",
    "vue": "^2.7.0"
  },
  "devDependencies": {                     // 开发依赖（≈provided）
    "sass": "^1.69.0",
    "webpack": "5.x"
  }
}
```

三件套认知：
- **package.json**：声明依赖和脚本；
- **package-lock.json**：锁版本（≈Maven 的固定版本，必须提交 git）；
- **node_modules/**：实际安装的包（≈Maven 本地仓库，用 gitignore 排除，npm install 重建）。

面试可能问："package-lock.json 有什么用？"——锁住依赖树，保证所有人/CI 构建一致。

## 8.4 webpack / vite：构建打包是干什么的

浏览器不认识 `@/`、不认识 .vue 文件、不认识 ES Module 里 import 的图片，
所以开发写的是"增强版 JS"，需要**构建工具**编译成浏览器能跑的东西：

```
源码（Vue SFC / ES Module / SCSS / 别名）
   ↓  构建（webpack/vite）
浏览器可运行的 JS bundle + CSS + 静态资源（带 hash 文件名）
```

webpack 几个常听词的通俗解释（面试能说清就赢）：

| 名词 | 通俗解释 | Java 类比 |
|------|---------|----------|
| entry | 入口文件，从这里开始找依赖 | main() |
| loader | 处理"非 JS"文件（scss→css、图片） | 类型转换器 |
| plugin | 构建期的额外能力（Copy/压缩） | Maven 插件 |
| bundle | 最终打包出的一坨 JS | 可执行 jar |
| HMR | 开发时改代码热更新，不刷新页面 | dev-tools 热重载 |
| tree-shaking | 只打包用到的代码（未用导出被摇掉） | 死代码消除 |

vite vs webpack：vite 开发环境用原生 ESM 按需编译（启动快到秒级），
webpack 全量打包（Vue CLI 时代标准）。面试可提"vite 是新一代，dev 更快；webpack 生态最全"。

## 8.5 RuoYi-Vue 前端目录解剖（打开项目对照）

```
ruoyi-ui/
├── package.json              // 依赖与脚本
├── vue.config.js             // webpack 配置：代理、别名、打包优化
├── public/                   // 不打包的静态资源（index.html 模板）
└── src/
    ├── main.js               // 入口：new Vue + 挂载路由/store
    ├── App.vue               // 根组件（布局容器）
    ├── api/                  // 接口定义（listDevice 等，每个模块一个文件）
    ├── assets/               // 静态资源 + styles（第9章讲过 scss 结构）
    ├── components/           // 通用组件（Pagination、Editor…）
    ├── layout/               // 整体布局（侧栏/导航/标签页）
    ├── router/               // 路由配置（页面路径 ↔ 组件）
    ├── store/                // Vuex 全局状态（token/用户信息/权限）
    ├── utils/                // 工具（request.js、auth.js、auth 权限）
    └── views/                // 页面组件（每页一个 .vue）
```

数据流主链路（面试能画出来就是"懂了 RuoYi 前端"）：

```
页面 views/xxx.vue
  → api/xxx.js（import request）
  → utils/request.js（axios 拦截器：加 token、解业务码）
  → 后端 Spring Boot 接口
  ← 响应 {code:200,data:{...}}
  → 页面 data/表格渲染
```

权限相关（RuoYi 特色）：
- store 里存权限点（permission 集合）；
- 菜单/按钮用 v-hasPermi 指令控制显示；
- 路由守卫 beforeEach：没 token → 跳登录页。

```js
// router 守卫（面试可讲："路由访问前检查登录态和权限"）
router.beforeEach((to, from, next) => {
  if (getToken()) {
    next();                       // 有 token 放行
  } else {
    next(`/login`);               // 没 token 去登录
  }
});
```

## 8.6 环境变量：开发/测试/生产配置分离

```
# 根目录 .env.development / .env.production
# RuoYi 示例：
VUE_APP_BASE_API = '/dev-api'        # 开发：走 devServer 代理
# .env.production
VUE_APP_BASE_API = 'https://api.example.com'   # 生产：直连后端域名
```

注意（记忆里有过）：**VUE_APP_BASE_API 在构建时被"烤进"打包产物**——
生产改 IP 不能只改配置，得重新构建；或用外部脚本替换 dist 里的 js（你项目踩过的坑）。

## 8.7 常见坑快查

| 坑 | 现象 | 解法 |
|----|------|------|
| import 路径报错 | 相对路径写错 | 用 @/ 别名（配好的直接用） |
| 改 node_modules 生效 | 包被还原 | 别改依赖；用 npm patch 或提 issue |
| node 版本不匹配 | npm install 报错 | 用 nvm 切版本（RuoYi 老项目要 Node 12-14） |
| 生产样式/功能异常 | dev 正常 | 对比环境变量与构建配置；看打包警告 |
| 打包巨大 | 全量引了三方库 | 按需引入（babel-plugin-component） |

## 8.8 面试自测

- Q：ES Module 与 CommonJS 区别？
  A：ESM import/export 静态分析（可 tree-shaking），CJS require/module.exports 动态加载。
- Q：package-lock.json 作用？
  A：锁依赖树版本，保证构建一致，必须提交。
- Q：webpack 构建流程？
  A：从 entry 出发解析依赖 → loader 处理非 JS → 插件优化 → 输出带 hash 的 bundle。
- Q：RuoYi 前端请求流程？★
  A：页面 → api → request.js（token+错误处理）→ 后端 → code 解包渲染。
- Q：打包产物的 hash 有什么用？
  A：内容变 hash 变，强制浏览器更新缓存（发布不白屏）。

## 小结

- ES Module：作用域隔离 + 显式依赖 + 按需加载。
- npm 管依赖（package.json/lock），webpack 打包（entry/loader/plugin）。
- RuoYi 数据流：页面 → api → request 拦截器 → 后端 → 渲染。
- 环境变量构建时注入，生产改 IP 要重新打包（或替换产物）。
