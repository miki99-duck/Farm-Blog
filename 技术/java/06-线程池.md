# 第6章 线程池：七大参数、四种拒绝策略与核心流程

> 一句话讲清：**线程池是"线程的复用 + 任务的排队 + 拒绝的兜底"——
> 生产环境禁止 `new Thread()` 和 `Executors.xxx()`，必须用 `ThreadPoolExecutor` 显式构造。**
> 本章目标：背熟 7 大参数、4 种拒绝策略、核心流程；能手写生产可用的线程池配置。

## 6.1 为什么用线程池

```java
// ❌ 反例：new Thread
public void handle(Request req) {
    new Thread(() -> {
        process(req);
    }).start();   // 每次请求都创建线程
}
// 问题：
// 1 线程创建/销毁开销大（约几 MB 栈空间 + OS 调度）
// 2 并发暴涨时创建几千个线程 → OOM / 上下文切换拖垮
// 3 没有容量控制、没有任务排队、没有拒绝机制

// ✅ 正例：线程池
private final ExecutorService pool = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
public void handle(Request req) {
    pool.submit(() -> process(req));   // 任务交给池
}
```

**线程池的三大优势：**
1. **降低创建销毁成本**：线程复用，池化
2. **资源控制**：限制最大线程数，防止 OOM
3. **任务管理**：排队、超时、拒绝、监控

## 6.2 ThreadPoolExecutor 七大参数（★ 面试必背）

```java
// 构造签名
public ThreadPoolExecutor(
    int corePoolSize,               // ① 核心线程数
    int maximumPoolSize,            // ② 最大线程数
    long keepAliveTime,             // ③ 空闲存活时间
    TimeUnit unit,                  // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 工作队列
    ThreadFactory threadFactory,    // ⑥ 线程工厂
    RejectedExecutionHandler handler // ⑦ 拒绝策略
)
```

### 参数详解

| # | 参数 | 含义 | 配置建议 |
|---|------|------|----------|
| ① | corePoolSize | 常驻线程数 | CPU 密集型：核数 + 1；IO 密集型：2 × 核数（或更高） |
| ② | maximumPoolSize | 最大线程数 | 通常 2~4 × core |
| ③ | keepAliveTime | 非核心线程空闲多久销毁 | 60s 常见 |
| ④ | unit | 时间单位 | SECONDS |
| ⑤ | workQueue | 任务队列 | 见下 |
| ⑥ | threadFactory | 线程工厂 | 给线程起名字（默认无名，排查问题困难） |
| ⑦ | handler | 拒绝策略 | 见 6.5 |

### 三种队列怎么选（★ 高频）

| 队列 | 容量 | 特点 | 适用 |
|------|------|------|------|
| `ArrayBlockingQueue` | **有界** | 内存可控，FIFO | 大多数生产场景（推荐） |
| `LinkedBlockingQueue` | 默认**无界**（Integer.MAX_VALUE） | 内存风险 | 谨慎，避免 OOM |
| `SynchronousQueue` | **不存任务** | 来了直接派线程 | 任务必须立即处理（如 Tomcat） |
| `PriorityBlockingQueue` | 无界 | 按优先级出队 | 任务有优先级 |
| `DelayQueue` | 无界 | 延时任务 | 延迟执行（如延迟队列） |

**追问：为什么 `Executors.newFixedThreadPool()` 危险？**
答："它的队列是 `LinkedBlockingQueue()`（默认无界），
高并发下任务无限堆积 → 内存溢出。
**正确做法**：用 `ThreadPoolExecutor` 构造，队列显式设上限。"

### 常见配置对比

```java
// ① CPU 密集型（计算为主，线程切换成本高）
new ThreadPoolExecutor(C, C, 0, SECONDS, new LinkedBlockingQueue<>());

// ② IO 密集型（等外部响应，线程大量阻塞）
new ThreadPoolExecutor(2*C, 4*C, 60, SECONDS, new ArrayBlockingQueue<>(200));

// ③ 混合型（业务代码常见）
new ThreadPoolExecutor(8, 16, 60, SECONDS, new ArrayBlockingQueue<>(500));
```

## 6.3 核心流程（★ 必考）

**任务提交的真实执行路径（面试必画）：**

```
提交任务 task
    │
    ▼
┌─────────────────────────────────────────────┐
│ ① 当前线程数 < corePoolSize ?                  │
│    → 创建新核心线程执行 task                    │
│    → 否则进入 ②                               │
├─────────────────────────────────────────────┤
│ ② 队列未满 ?                                   │
│    → 加入队列 workQueue                       │
│    → 否则进入 ③                               │
├─────────────────────────────────────────────┤
│ ③ 当前线程数 < maximumPoolSize ?              │
│    → 创建新非核心线程执行 task                  │
│    → 否则进入 ④                               │
├─────────────────────────────────────────────┤
│ ④ 队列满 + 线程满 → 执行拒绝策略                │
│    → AbortPolicy / CallerRunsPolicy / ...     │
└─────────────────────────────────────────────┘
```

**追问：为什么"先队列后线程"而不是"先线程后队列"？**
答："因为队列能缓存突发任务，非核心线程创建有开销（线程栈几 MB + OS 调度），
**优先把任务排队比直接创建新线程便宜**。
只有队列满了，才创建非核心线程。"

**追问：如果队列满了，非核心线程会销毁吗？**
答："会——空闲超过 keepAliveTime 的非核心线程会被回收（`allowCoreThreadTimeOut(true)` 时核心线程也回收）。"

## 6.4 四种内置拒绝策略（★ 必背）

```java
// 当 ④ 阶段触发（队列满 + 线程满）时执行
public class RejectedExecutionHandler {
    void rejectedExecution(Runnable r, ThreadPoolExecutor e);
}
```

| 策略 | 行为 | 适用 |
|------|------|------|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 默认；调用方需处理异常 |
| `CallerRunsPolicy` | 调用方线程执行（同步） | 限流：让上游"减速" |
| `DiscardPolicy` | 静默丢弃 | 非关键任务（如埋点） |
| `DiscardOldestPolicy` | 丢队列头，重试新任务 | 新任务更重要（如实时告警） |

### 自定义拒绝策略（生产常用）

```java
// 场景：任务很重要，但内存快满了，要告警 + 异步持久化
public class CustomHandler implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        log.error("线程池已满，任务被拒绝：{}", r);
        // 1. 持久化任务到数据库/队列（不丢）
        asyncTaskDao.save(r);
        // 2. 告警
        monitor.alert("线程池饱和");
    }
}
```

**追问：拒绝策略怎么选？**
答："按业务容忍度：
- 关键任务不能丢 → 自定义（落库+告警）
- 可丢失 → DiscardPolicy
- 希望上游减速 → CallerRunsPolicy（限流效果）
- 实时性优先 → DiscardOldestPolicy"

## 6.5 线程池的监控（★ 加分）

```java
// 线程池暴露了大量监控指标
ThreadPoolExecutor pool = ...;

// 当前活跃线程数
pool.getActiveCount();

// 已创建线程总数
pool.getPoolSize();

// 已完成任务数
pool.getCompletedTaskCount();

// 队列中任务数
pool.getQueue().size();

// 是否已 shutdown
pool.isShutdown();

// 生产做法：定期打日志 / 上报 Prometheus
ScheduledExecutorService monitor = Executors.newSingleThreadScheduledExecutor();
monitor.scheduleAtFixedRate(() -> {
    log.info("Pool[active={}, queue={}, completed={}, threads={}]",
        pool.getActiveCount(),
        pool.getQueue().size(),
        pool.getCompletedTaskCount(),
        pool.getPoolSize());
}, 10, 10, TimeUnit.SECONDS);
```

## 6.6 Executors 工厂方法剖析（★ 高危）

```java
// ❌ 生产禁止使用 Executors.xxx() —— 阿里巴巴规范第 1 条
Executors.newFixedThreadPool(4);        // 队列无界 → OOM
Executors.newCachedThreadPool();        // 线程无上限 → OOM
Executors.newSingleThreadExecutor();    // 队列无界 → OOM
Executors.newScheduledThreadPool(4);    // 队列无界 → OOM

// ✅ 正确：用 ThreadPoolExecutor 显式构造
new ThreadPoolExecutor(4, 4, 0, SECONDS, new ArrayBlockingQueue<>(100));
```

**追问：为什么阿里巴巴规范禁止 Executors？**
答："它们内部用了无界队列，生产环境无法承受突发流量——队列无限堆积，
内存被填满 OOM。**用 ThreadPoolExecutor 显式设上限**，队列容量、拒绝策略都要自己定。"

## 6.7 优雅关闭（★ 生产必做）

```java
// 应用关闭前
pool.shutdown();          // 1. 不再接受新任务，等待已提交任务完成
// 或
pool.shutdownNow();       // 2. 立即停止（中断正在跑的任务，返回未执行的任务列表）

// 生产关闭流程：
pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {   // 最多等 30 秒
    pool.shutdownNow();                                // 超时强制关
}
```

**Spring Boot 应用关闭线程池（JVM ShutdownHook）：**
```java
// 注册关闭钩子，确保进程退出前任务完成
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    pool.shutdown();
    try {
        if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
            pool.shutdownNow();
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
    }
}));
```

## 6.8 参数怎么定：CPU 密集 vs IO 密集（★ 高频追问）

### CPU 密集型 vs IO 密集

```java
// CPU 密集：计算为主（排序、压缩、加密）
// 线程切换成本高，线程越多越卡 → 线程数 = 核数 + 1
Runtime.getRuntime().availableProcessors();   // 当前可用核数

// IO 密集：等待外部响应（HTTP、DB、文件）
// 大部分时间线程在等 IO，不是忙 → 线程数 = 核数 × (1 + IO等待/CPU时间)
// 经验值：2~4 倍核数
```

**追问：怎么估算 IO 线程数？**
答："用 Little 定律：`线程数 = 目标 QPS × 平均响应时间`。
比如目标 1000 QPS，单次请求 50ms → 需要 50 个线程。
**注意**：线程不是越多越好——超过某个点后上下文切换和内存反而拖慢吞吐。"

**追问：核数 + 1 的 "+1" 是干什么的？**
答："万一某个线程被 OS 调度切换出去，CPU 不会闲置——留一个线程顶上。
**本质**：防止某个线程被让出时 CPU 空转。"

## 6.9 动态线程池（★ 加分项，生产进阶）

**固定参数写死了很难调——动态线程池可以运行时改 core/max/queue。**

```java
// 阿里有开源框架 DynamicTp；Spring 生态有 spring-cloud-starter-dynamic-threadpool
// 核心思路：从配置中心（Nacos/Apollo）读 core/max，监听配置变更实时调用 setCorePoolSize 调整

// 简化版：Spring 注入 @ConfigurationProperties 绑定，配置中心改了自动刷新
@Configuration
@ConfigurationProperties(prefix = "pool")
@RefreshScope   // Spring Cloud 的刷新范围，配置变更后重建 Bean
public class PoolConfig {
    private int core = 8;
    private int max = 16;
    private int queue = 500;
    // getter/setter
}

// 配置中心改了 core → refresh 触发 setCorePoolSize
pool.setCorePoolSize(config.getCore());
pool.setMaximumPoolSize(config.getMax());
// 支持运行时调整，不用重启
```

**追问：什么时候用动态线程池？**
答："多实例部署，不同环境（开发/测试/生产）资源不同；或者业务量波动大需要灵活调整。
**代价**：多了配置中心依赖，运维复杂度上升。**单机应用用固定参数即可。**"

## 6.10 线程池常见坑汇总

| # | 坑 | 现象 | 解决 |
|---|----|------|------|
| 1 | `Executors.xxx()` | OOM | 用 `ThreadPoolExecutor` 显式构造 |
| 2 | 队列无界 | 内存爆 | `ArrayBlockingQueue(有界)` |
| 3 | 核心线程数太大 | 线程切换开销 | 按 CPU/IO 类型设 |
| 4 | 没设 threadFactory | 排查问题难 | 给线程起名字 |
| 5 | 没设拒绝策略 | 抛异常任务丢失 | 自定义 handler |
| 6 | 没监控 | 不知道饱和 | 定期打日志 |
| 7 | 没优雅关闭 | 数据丢失 | shutdown + awaitTermination |
| 8 | 用 new Thread 裸写 | 不可控 | 禁止 |
| 9 | 死循环任务 | 池被占满 | 任务要有超时 |
| 10 | 嵌套提交 | 死锁 | 避免在池内提交到同一池 |

## 6.11 面试自测（追问链）

**Q1:线程池 7 大参数？**
一句话:"core / max / keepAlive / unit / workQueue / threadFactory / handler。"
追问:参数怎么定?(CPU 密集 = 核+1，IO 密集 = 2×核，按 QPS×RT 估算)

**Q2:线程池核心流程？**
一句话:"① 核心线程未满 → 建核心；② 队列未满 → 排队；③ 最大未满 → 建非核心；④ 都满 → 拒绝。"
追问:为什么先队列后线程?(队列排队比建新线程便宜，非核心线程销毁有成本)

**Q3:4 种拒绝策略？**
一句话:"Abort 抛异常、CallerRuns 调用方跑、Discard 静默丢、DiscardOldest 丢最旧。"
追问:生产常用哪个?(自定义：告警+落库；或 CallerRuns 做限流)

**Q4:为什么禁止 Executors？**
一句话:"用了无界队列，高并发下任务堆积 OOM；要 ThreadPoolExecutor 显式上限。"

**Q5:怎么优雅关闭线程池？**
一句话:"shutdown() 不再接受新任务 + awaitTermination 等待 + 超时 shutdownNow 强制关。"
追问:为什么生产必须做?(避免进程退出时任务丢失)

**Q6:怎么监控线程池？**
一句话:"getActiveCount/PoolSize/CompletedTaskCount/Queue.size 定期打日志或上报。"
追问:动态线程池?(阿里 DynamicTp / spring-cloud-dynamic，运行时改 core/max)
