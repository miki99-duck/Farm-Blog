# 第7章 多线程与锁面试速查（40 题速刷）

> 面试定位：考前 30 分钟只刷这一章。每题"一句话答案 + 追问 1~3 步"。
> 用法：先读问题 → 回忆答案 → 对比 → 不懂的回头看对应章节。

## 7.1 线程基础（6 题）

### Q1:JVM 线程有几个状态？和 OS 线程状态的区别？

**答**：6 个——NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED。
OS 多了 READY 状态，JVM 把"等 CPU"也归入 RUNNABLE。

**追问 1**：BLOCKED 和 WAITING 区别？
BLOCKED 专指抢 synchronized 锁失败；WAITING 是主动等通知（wait/join/park）。

**追问 2**：sleep 是 TIMED_WAITING，wait 是 WAITING，对吗？
基本对。sleep(n) → TIMED_WAITING；wait() → WAITING；wait(n) → TIMED_WAITING。

### Q2:四种启动线程方式？

**答**：继承 Thread（不推荐）、实现 Runnable（主流）、Callable+FutureTask（需要返回值）、线程池（生产唯一推荐）。

**追问**：Runnable vs Callable？
Callable 有返回值（`V call()`）、能抛受检异常，必须包进 FutureTask。

### Q3:怎么优雅停止一个线程？

**答**：volatile 标志位循环检查 或 interrupt() + catch 里退出。stop()/suspend() 已废弃。

**追问**：为什么 stop 废弃？
不释放锁、不清理资源，可能数据不一致。

### Q4:什么是守护线程？有什么坑？

**答**：后台线程，用户线程都结束后自动终止。坑：setDaemon 必须在 start 之前调，且它不等 ShutdownHook。

### Q5:ThreadLocal 为什么必须 remove？

**答**：线程池里线程复用，不 remove 会串数据；ThreadLocalMap 的 value 强引用，不 remove 会内存泄漏。

**追问**：怎么实现的？
Thread 类里有 ThreadLocalMap，key 是 WeakReference(ThreadLocal)，value 是强引用。

### Q6:线程优先级？

**答**：1~10，只是调度倾向不保证。优先级只是 CPU 时间片分配的偏好，不保证一定先跑。

## 7.2 线程安全与 volatile（8 题）

### Q7:什么是线程安全？

**答**：多线程同时调用时始终得到正确结果，不需要额外同步。

**追问**：线程安全 = 没有并发？
不是——是"并发结果正确"。

### Q8:线程安全三大问题？

**答**：原子性（i++ 被插队）、可见性（改了别人看不到）、有序性（指令被重排）。

**追问 1**：volatile 解决哪个？
解决可见性 + 有序性，**不解决原子性**。

**追问 2**：怎么解决原子性？
synchronized / ReentrantLock / AtomicInteger 等原子类。

### Q9:volatile 底层原理？

**答**：写时插内存屏障刷回主内存，读时强制从主内存读、禁指令重排。

**追问**：为什么不是 mutex？
volatile 基于 CPU 内存屏障，不是互斥锁，开销比 synchronized 小。

### Q10:volatile 的"两能一不能"？

**答**：能保可见性、能保有序性，不能保原子性（复合操作）。

**追问**：volatile 修饰 i++ 安全吗？
不安全——`count++` 是"读-加-写"三步，volatile 只管单次读写。

### Q11:为什么 DCL 必须 volatile？

**答**：没 volatile 时，`new Singleton()` 可能被重排成"先赋值后初始化"，
另一线程读到"instance 非 null 但对象未构造完"→ NPE。

**追问**：为什么双重检查？
第一次不加锁走快路径；第二次锁内防止重复创建。

### Q12:什么是 JMM（Java 内存模型）？

**答**：程序员和 JVM 之间的"内存契约"，规定什么操作什么时候可见、按什么顺序。

**追问**：happens-before 是什么？
定义操作顺序的契约——A hb B 表示 A 的结果对 B 可见、不会重排到 B 之后。

### Q13:volatile 适合哪些场景？

**答**：状态标志（running flag）、单例 DCL、安全发布共享对象、双检锁。

**追问**：volatile 适合复合操作吗？
不适合——复合操作要加锁或用原子类。

### Q14:volatile 和 synchronized 区别？

**答**：volatile 不互斥、不阻塞；synchronized 互斥、阻塞。volatile 轻量但功能少。

## 7.3 synchronized（7 题）

### Q15:synchronized 锁的是什么？

**答**：对象引用。实例方法锁 this、静态方法锁 Class、代码块锁显式引用。

**追问**：不同实例同步吗？
不同实例锁不同 this，不互斥。

### Q16:synchronized 怎么实现的？

**答**：字节码 monitorenter/monitorexit + 对象头的 Monitor 管程。

**追问 1**：可重入怎么实现？
Monitor 的 owner + count，同线程重入只 count++。

**追问 2**：为什么异常也能释放锁？
字节码的异常表覆盖 monitorexit，异常也走退出路径。

### Q17:锁升级四阶段？

**答**：无锁 → 偏向锁（JDK15 禁）→ 轻量级锁（CAS 自旋）→ 重量级锁（Monitor + OS）。

**追问**：为什么升级？
无竞争零开销，有竞争逐步加重——JDK 1.6 引入。

### Q18:wait 和 sleep 区别？

**答**：wait 释放锁需 synchronized 块内调，notify 唤醒；sleep 不释放锁不需要锁，时间到自然醒。

**追问**：wait 为啥要在 while 里？
防虚假唤醒——被唤醒后条件可能又变回 false。

### Q19:死锁四条件？

**答**：互斥、持有并等待、不可剥夺、循环等待。

**追问**：怎么破？
按顺序拿锁（破循环等待）、tryLock 超时（破持有并等待）、缩小锁粒度。

### Q20:synchronized 和 ReentrantLock 区别？

**答**：synchronized 简单自动释放；ReentrantLock 可中断/可超时/可公平/多条件但必须手动 unlock。

**追问**：优先用哪个？
简单场景 synchronized（不易出错）；复杂需求 ReentrantLock。

### Q21:JDK 1.6 对 synchronized 的优化？

**答**：偏向锁、轻量级锁（锁升级）、锁消除、锁粗化、自适应自旋。

## 7.4 ReentrantLock 与 AQS（6 题）

### Q22:ReentrantLock 基本用法？

**答**：`lock.lock(); try { 业务 } finally { lock.unlock(); }`——finally 必须解锁。

**追问**：unlock 不在锁内会怎样？
抛 IllegalMonitorStateException。

### Q23:公平锁和非公平锁？

**答**：非公平锁直接 CAS 抢失败才排队（性能高）；公平锁按 FIFO 排队（避免饥饿但慢）。默认非公平。

### Q24:什么是 AQS？

**答**：AbstractQueuedSynchronizer，JUC 同步框架基类，用一个 volatile int state + CLH 队列管理锁状态和等待线程。

**追问**：state 是什么？
不同子类不同含义：ReentrantLock 存重入次数、Semaphore 存许可数、CountDownLatch 存倒计时。

### Q25:Condition 有什么用？

**答**：多条件等待——生产者消费者里 notFull 和 notEmpty 各等各的，不误唤醒。

**追问**：synchronized 有这功能吗？
没有——notify 只能唤醒等这个 monitor 的任意线程。

### Q26:tryLock 和 lock 怎么选？

**答**：需要"抢不到就放弃"用 tryLock（限流、避免死锁）；必须执行用 lock。

### Q27:AQS 的实现模式？

**答**：模板方法 + 状态机——子类实现 tryAcquire/tryRelease 修改 state，AQS 负责排队、自旋、park。

**追问**：为什么 park 不用 wait？
LockSupport.park 是底层原语，比 wait 灵活，不需要 monitor。

## 7.5 CAS 与原子类（4 题）

### Q28:CAS 是什么？

**答**：Compare And Swap，硬件原子指令，比较并交换三步不可打断，失败自旋重试。

**追问 1**：优点？
无阻塞、低竞争下快。

**追问 2**：缺点？
高竞争自旋浪费 CPU、ABA 问题。

### Q29:AtomicXxx 怎么实现的？

**答**：字段是 volatile + 方法用 CAS 循环（Unsafe.compareAndSwap）。

**追问**：为什么字段要 volatile？
保证可见性——一个线程改了别人立刻看到。

### Q30:ABA 问题？

**答**：值改走又改回，CAS 误以为没被改过。解：AtomicStampedReference（值+版本号）。

### Q31:AtomicLong vs LongAdder？

**答**：AtomicLong 单值 CAS 高竞争自旋；LongAdder 分片累加高竞争更快但要 sum。

## 7.6 线程池（5 题）

### Q32:线程池 7 大参数？

**答**：core / max / keepAlive / unit / workQueue / threadFactory / handler。

**追问**：参数怎么定？
CPU 密集 = 核+1，IO 密集 = 2×核，按 QPS×RT 估算。

### Q33:线程池核心流程？

**答**：① 核心线程未满→建核心；② 队列未满→排队；③ 最大未满→建非核心；④ 都满→拒绝。

**追问**：为什么先队列后线程？
队列排队比建新线程便宜，非核心线程销毁有成本。

### Q34:4 种拒绝策略？

**答**：Abort 抛异常、CallerRuns 调用方跑、Discard 静默丢、DiscardOldest 丢最旧。

**追问**：生产常用哪个？
自定义（告警+落库）；或 CallerRuns 做限流。

### Q35:为什么禁止 Executors？

**答**：内部用无界队列，高并发下任务堆积 OOM。要 ThreadPoolExecutor 显式设上限。

### Q36:怎么优雅关闭线程池？

**答**：shutdown() 不再接受新任务 + awaitTermination 等待 + 超时 shutdownNow 强制关。

## 7.7 项目结合 & 综合题（5 题）

### Q37:你在项目里用过多线程吗？（简历必问）

**话术（用 IoT 项目答）**：
"我在 IoT 平台用了三种场景：
① 用 `@Async` + 自定义 ThreadPoolExecutor 做 Kafka 消费的异步落库；
② 用 `CountDownLatch` 等所有批量任务完成；
③ 用 `AtomicInteger` 做请求级幂等号生成。
**关键设计**：
- 线程池参数：核心 4、最大 8、队列 200、CallerRunsPolicy 做限流
- 自定义 ThreadFactory 起名字便于排查
- 用 @ConfigurationProperties 绑配置中心支持动态调参
- 加了 activeCount / queue.size 监控打日志"

### Q38:线程安全你遇到过什么问题？

**话术**：
"遇到过'设备状态更新丢失'——两个消费者线程同时更新同一设备的状态，
后写覆盖前写。一开始以为是同步 bug，后来用 Thread dump 看到两个线程都在
synchronized 块外更新共享 Map。修复：把更新封装到 synchronized 方法里，
并且把共享 Map 换成 ConcurrentHashMap。
**教训**：线程安全的不是"代码加锁"，是"共享可变数据 + 多线程"——
先确认是不是真的共享、是不是真的可变。"

### Q39:你写过线程池吗？参数怎么定的？

**话术**：
"核心线程 4、最大 8、队列 200（ArrayBlockingQueue）、60s、CallerRunsPolicy、
自定义 ThreadFactory。
CPU 核数是 8，IO 密集型场景所以 max = 2×核；
队列有界防 OOM，CallerRuns 限流让上游感知；
监控每 10 秒打一次 activeCount 和 queue.size。"

### Q40:ReentrantLock 的 AQS 你理解吗？（深度追问）

**话术**：
"AQS 是一个抽象基类，核心就两样：一个 volatile int state 存锁状态，
一个 CLH 双向链表队列存等待线程。
ReentrantLock 的 tryAcquire：
- 非公平锁直接 CAS state 从 0 改到 1（第一次抢）
- 当前线程已持锁则 state++（可重入）
- 失败时加入队列尾，自旋 + park() 挂起
unlock 时 state-- 到 0 才真正释放，唤醒队列头节点。
Semaphore / CountDownLatch / ReadWriteLock 都基于 AQS，
只是 state 含义不同——Semaphore 是可用许可数，CountDownLatch 是倒计时。"

```
  │                └─ 无锁：CAS（Q28-31）

```

比如面试官问"volatile 能保证原子性吗"——顺着链：三大问题 → volatile → 不解决原子性 → CAS → ABA。
**背熟这条链，比背 40 题有用。**

## 7.9 高频坑速记（5 条）

1. **volatile 不能保原子性**——`count++` 用 AtomicInteger
2. **DCL 必须 volatile**——防指令重排
3. **ReentrantLock 必须 try-finally unlock**——否则死锁
4. **Executors 禁止裸用**——队列无界 OOM
5. **ThreadLocal 必须 remove**——线程池串数据 + 内存泄漏

## 7.10 一句话总结全书

**"线程安全的本质是'共享可变数据 + 多线程'；三大问题（原子性/可见性/有序性）是设计出发点；
volatile 轻但只能保可见性和有序性，synchronized 重但功能全，CAS 快但怕高竞争；
线程池是生产标配——禁止 new Thread、禁止 Executors 裸用，7 参数 + 核心流程 + 拒绝策略是必背。"**
